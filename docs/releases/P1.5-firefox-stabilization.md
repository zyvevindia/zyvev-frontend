## 1. Executive Summary

P1.5 fixes a class of Playwright E2E failures on **Firefox** where the Buyer Assistant test suite crashed with the global ErrorBoundary (`"Something Went Wrong"`) instead of rendering `.assistant-page`. The failures were caused by an artificial race between **Playwright’s extremely fast document-level navigation** and **Vite’s lazy-route CSS preloading** — not by a production bug in the assistant feature.

The fix introduces **deterministic outbound route stabilization** in `tests/helpers/assistantHelpers.js`. Before returning to `/assistant` via `page.goto()`, tests now wait for lazy-loaded destination routes (TCO calculator, vehicle detail, compare guide) to reach a stable terminal state. This eliminates Firefox’s `NS_BINDING_ABORTED` preload aborts without modifying application code, suppressing Vite errors, or patching the bundler.

**Scope:** One committed file. Zero production behavior changes.

## 2. Problem

### Symptom

On Linux CI, functional Playwright tests for `/assistant` failed consistently on **Firefox**, starting with:

```
tests/assistant/analytics.spec.js
  › registers assistant analytics events and fires handlers during journeys
```

**User-visible test failure:**

- Global ErrorBoundary rendered: heading `"Something Went Wrong"`
- Assertion failed: `.assistant-page` not visible
- `assertHealthyPage()` could pass briefly before the crash on some steps

### CI impact (pre-fix)

| Metric | Approximate value |
|--------|-------------------|
| Total functional tests (Linux CI) | 98 |
| Passed | ~63 |
| Failed | ~35 |
| Primary browser affected | Firefox |
| First failing spec | `analytics.spec.js` |

Tests often **passed locally on Windows/Chromium** but failed on **Linux/Firefox**, which made the issue appear environment-specific and delayed root-cause identification.

### First JavaScript exception (production preview build)

```
Error: Unable to preload CSS for /assets/score2-BAgIZztY.css
```

This error originated from Vite’s injected `__vitePreload` helper in the production bundle, not from assistant application logic directly.

## 4. Root Cause

### Causal chain

```
analytics.spec.js
  │
  ├─ click "Estimate Ownership Cost"  →  client nav to /tools/tco
  │     └─ React.lazy(TcoCalculatorPage) → __vitePreload(deps)
  │           └─ deps include score2-BAgIZztY.css (Score2ToolsPerspective)
  │
  ├─ ~35–45ms later: completeAssistantToResults(..., { navigate: true })
  │     └─ startAssistant() → page.goto("/assistant")   ← document-level navigation
  │
  ├─ Browser aborts in-flight stylesheet request
  │     Firefox: NS_BINDING_ABORTED
  │     Chromium: net::ERR_ABORTED (may not always propagate to ErrorBoundary)
  │
  ├─ Vite __vitePreload CSS helper
  │     └─ <link> "error" event → reject(Error("Unable to preload CSS for …"))
  │           └─ handlePreloadError() → vite:preloadError (not prevented) → throw
  │
  └─ Global ErrorBoundary
        └─ "Something Went Wrong" — .assistant-page never renders
```

The same pattern occurred when tests clicked **"View Vehicle"** (`/cars/…` → `CarDetails` → `SimilarEvsSection` → score2 CSS) and returned to `/assistant` via `page.goto()`.

### What was NOT the cause

| Disproved hypothesis | Evidence |
|---------------------|----------|
| `/assistant` directly loads `score2.css` | `BuyerAssistantPage` `__vite__mapDeps` does not include score2 CSS index |
| Missing asset / 404 | `dist/assets/score2-BAgIZztY.css` exists in build output |
| Initial `page.goto("/assistant")` at test start | No score2 requests on first navigation in timeline |
| Production assistant bug | Race requires sub-human navigation timing; real users rarely trigger it |

## 5. Why Firefox Behaved Differently

Both Firefox and Chromium **abort** in-flight network requests when a document navigation unloads the current page. The difference is how that abort surfaces to JavaScript:

| Behavior | Firefox | Chromium |
|----------|---------|----------|
| Aborted stylesheet | Reports `NS_BINDING_ABORTED`; `<link rel="stylesheet">` fires **`error`** event | Reports `net::ERR_ABORTED`; may not always propagate rejection into global ErrorBoundary |
| Vite preload handling | Treats `<link>` error as fatal → throws `"Unable to preload CSS for …"` | Same Vite code path, but less consistently fatal in observed CI |
| CI outcome | **Reliable failure** on assistant cross-route tests | Often passed the same tests |

Firefox’s stricter surfacing of aborted stylesheet loads as `<link>` error events made the Vite preload helper throw reliably. Chromium’s behavior masked the race in some runs, which is why the issue appeared **Firefox-specific in CI** while passing locally on Chrome.

**Important:** This is a **test timing artifact**, not a Firefox production defect. Real users navigating at human speed typically allow lazy routes to paint before leaving.

## 6. Why the Application Was Not at Fault

### Production navigation timing

Real users clicking from assistant results into TCO or vehicle detail pages do not typically invoke another **full document navigation** back to `/assistant` within tens of milliseconds. Human interaction, paint, and reading time allow Vite CSS preloads to complete or fail on the **active route** — not on an abandoned one.

### Vite preload behavior is intentional

Vite preloads CSS for lazy chunks **before** evaluating the async module to prevent FOUC (flash of unstyled content). When a stylesheet genuinely fails (404, deploy skew, network error) on the **current route**, throwing is correct behavior. The assistant application correctly relies on this mechanism.

### No application code change was required

The approaches below were considered during investigation. Formal accept/reject decisions are recorded in [§7 Engineering Decisions (ADR)](#7-engineering-decisions-adr).

| Approach considered | Why rejected |
|--------------------|--------------|
| Suppress `vite:preloadError` in `main.jsx` | Masks real deploy-skew and 404 failures for all users |
| Eager-import `score2.css` in non-lazy parent | Increases initial bundle; does not fix test navigation race |
| Patch Vite `__vitePreload` | High maintenance; no upstream abort-detection for `<link>` errors |
| Move `assistant.css` to `main.jsx` (`ddf43140`) | Did not change CI outcome; root cause was elsewhere |

The failure was **Playwright calling `page.goto("/assistant")` too soon** after entering lazy routes that had started but not finished CSS preloads.

## 7. Engineering Decisions (ADR)

This section records the key engineering decisions made during the P1.5 investigation, including approaches that were deliberately rejected. It is written as lightweight Architecture Decision Record (ADR) material so future contributors understand the rationale behind the chosen fix and do not revisit previously discarded solutions without new evidence. For a summary of why production code was ruled out, see also [§6 Why the Application Was Not at Fault](#6-why-the-application-was-not-at-fault).

During root-cause analysis, four fix strategies were evaluated against Options A (application change), B (test helper), and C (Vite patch). The outcomes below are the authoritative record.

### Decision 1 — Do not suppress `vite:preloadError` globally

**Decision:** Do not add a global `window.addEventListener("vite:preloadError", …)` handler that calls `preventDefault()` for CSS preload failures.

**Reason:** Vite emits `vite:preloadError` when dynamic imports or lazy CSS fail to load. Suppressing these errors in production would hide **genuine deployment failures** — stale chunk references after a deploy, missing assets, and network errors that real users must recover from (typically via reload).

**Rejected alternative:** Option A — minimal application change in `main.jsx` to swallow `"Unable to preload CSS for …"` errors.

---

### Decision 2 — Do not patch Vite

**Decision:** Do not fork, patch, or maintain a custom build plugin that rewrites Vite’s injected `__vitePreload` helper.

**Reason:** Patching Vite creates **long-term maintenance burden** — every Vite upgrade requires re-applying the patch, and the `<link>` `error` event still cannot reliably distinguish navigation abort from genuine failure.

**Rejected alternative:** Option C — framework/runtime fix via `pnpm patch vite` or upstream contribution.

---

### Decision 3 — Fix the Playwright helper instead of production code

**Decision:** Introduce `waitForLazyRouteStabilized()` and `navigateToAssistant()` in `tests/helpers/assistantHelpers.js`.

**Reason:** The failure was an **artificial E2E navigation race**. Playwright called `page.goto("/assistant")` within ~35–45 ms of entering lazy routes (`/tools/tco`, `/cars/…`, `/compare/…`), abandoning in-flight Vite CSS preloads. Adjusting test navigation timing fixes the race at the layer where it was introduced.

**Selected approach:** Option B — test helper improvement.

---

### Decision 4 — Keep production behavior unchanged

**Decision:** No changes to application code, routing, Vite configuration, or ErrorBoundary behavior for this release.

**Reason:** **Real users do not navigate away within 35–45 ms** of entering a lazy route. Human interaction, paint time, and reading delay allow preloads to complete on the active route. Production Vite preload semantics (throw on genuine CSS failure) remain correct and must not be weakened for a test-only timing issue.

**Implication:** Commit `7a432986` touches one test file only. No user-facing behavior changes.

## 8. Solution

### Commit

Single-file change in test helpers only. See [§13 Related Commits](#13-related-commits).

### New API surface (`tests/helpers/assistantHelpers.js`)

| Function | Purpose |
|----------|---------|
| `waitForLazyRouteStabilized(page)` | No-op on `/assistant` or unregistered routes; otherwise waits for route stability |
| `navigateToAssistant(page)` | `waitForLazyRouteStabilized()` then `page.goto("/assistant")` |
| `startAssistant(page, { navigate: true })` | Now calls `navigateToAssistant()` instead of bare `page.goto()` |

### Stabilization registry

Outbound lazy routes reached from assistant result links are registered in `OUTBOUND_LAZY_ROUTE_STABILIZERS`:

| Route | Readiness gate |
|-------|----------------|
| `/tools/tco` | URL match → TCO page heading (`Total Cost of Ownership`) → `load` → no ErrorBoundary |
| `/cars/:slug` | URL match → `.cd-page` mounted → `load` → no ErrorBoundary |
| `/compare/:slug` | URL match → route started (loading shell or terminal UI) → loading skeleton gone → terminal state (guide hero, editorial, or "Guide not found") → `load` → no ErrorBoundary |

### Shared pipeline

All registered routes follow the same sequence:

1. Confirm destination URL
2. Route-specific `waitForReady` gate
3. `page.waitForLoadState("load")`
4. `assertHealthyPage()` (no global ErrorBoundary)

### Explicit non-goals

- No production code changes
- No Vite/Rolldown modifications
- No `vite:preloadError` suppression
- No arbitrary `waitForTimeout` sleeps
- No fallback `waitForLoadState` on unknown routes (preserves unrelated test behavior)

## 11. Lessons Learned

### 1. Follow the first exception, not the symptom

The ErrorBoundary showed `"Something Went Wrong"` but the actionable error was `"Unable to preload CSS for …"`. Fixing CSS import location without proving the exception was speculative and wasted a commit (`ddf43140`).

### 2. E2E races can be browser-specific without being browser bugs

Firefox’s reliable surfacing of aborted stylesheet `<link>` errors made a Playwright timing issue appear as a Firefox CI failure. The fix belongs in **test navigation discipline**, not browser workarounds in production.

### 3. Lazy-route CSS preloads are abandoned on hard navigation

`page.goto()` is a document-level navigation that aborts in-flight requests from the previous route. Client-side React Router navigation does not always exhibit the same timing. Tests that mix `<Link>` clicks with `page.goto()` back must account for Vite preload lifetimes.

### 4. Vite’s preload helper cannot distinguish abort from failure

The `<link>` `error` event does not expose `NS_BINDING_ABORTED`. Suppressing all CSS preload errors in production would hide real failures. Test-side stabilization is the correct layer.

### 5. Keep fixes scoped to the proven root cause

Option B (test helper) was chosen over app-level suppression and Vite patches because it fixes the artificial race without masking genuine user-facing preload failures. See [§7 Engineering Decisions (ADR)](#7-engineering-decisions-adr).

### 6. Self-contained commits aid release hygiene

Commit `7a432986` touches one file with no dependency on investigation artifacts (diagnostics, debug scripts, ErrorBoundary test mode). This allows P1.5 to merge independently of unfinished work in the working tree.

## 12. Future Maintenance Guidance

### Adding a new outbound lazy route

When assistant tests navigate away via a result link and return with `completeAssistantToResults({ navigate: true })` or `startAssistant({ navigate: true })`:

1. Open `tests/helpers/assistantHelpers.js`
2. Add an entry to `OUTBOUND_LAZY_ROUTE_STABILIZERS` with:
   - `label` — human-readable name
   - `pathname` — regex matching `URL.pathname`
   - `url` — Playwright URL assertion
   - `waitForReady` — stable route signal (prefer headings/product copy over deep layout selectors)
3. Shared `load` + `assertHealthyPage` run automatically via `finishLazyRouteStabilization`

### Selector stability guidelines

| Prefer | Avoid |
|--------|-------|
| Page headings with stable product copy | Deep component class chains |
| Route root containers (`.cd-page`) | Transient loading spinners alone |
| Loading shell **gone** + terminal state | Arbitrary `waitForTimeout` |

### When NOT to add a stabilizer

- Route is not lazy-loaded or does not preload split CSS via Vite
- Tests use client-side navigation back (e.g. in-app "Restart") instead of `page.goto`
- Tests pass `{ navigate: false }` while already on `/assistant`

### If the race reappears

1. Capture first `pageerror` / unhandled rejection (not just ErrorBoundary DOM)
2. Check network timeline for aborted CSS from **previous** route
3. Verify whether a new `page.goto()` was added immediately after a lazy route entry
4. Do **not** suppress `vite:preloadError` without product/engineering review
